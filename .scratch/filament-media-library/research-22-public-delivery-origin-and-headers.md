# Research: Public Delivery Origin and Headers

**Question:** How much control does the plugin have over a *public* Media Asset's delivery, where it is not in the request path? Specifically: whether Cloudflare R2 and S3-compatible drivers under Laravel's filesystem contract can set response headers (`Content-Security-Policy`, `Content-Disposition`, `Content-Type`) as stored object metadata at write time, and whether `league/flysystem-aws-s3-v3` exposes that through the standard `put()`/`writeStream()` options; how R2 custom domains and public bucket URLs interact with `Storage::disk()->url()` configuration and whether a configured CDN base URL is a thing the plugin should accept; and whether R2 or CloudFront can attach response headers at the edge independently of the stored object.

**Research date:** 2026-08-27. All sources below were accessed on that date. Laravel references use the official `13.x` branch source and the 13.x documentation; Flysystem references use the `3.x` branch of `thephpleague/flysystem-aws-s3-v3`; Cloudflare and AWS references are official vendor documentation.

**Local verification note:** this repository contains no `composer.json`, no `vendor/` directory and no PHP source (it holds `CONTEXT.md`, `AGENTS.md`, `docs/` and `.scratch/` only). There is no installed Laravel or Flysystem to read, so every version-specific fact below rests on upstream source rather than on a lockfile. Laravel 13's own documentation pins the S3 requirement as `league/flysystem-aws-s3-v3 "^3.0"`, which is the branch read here.

## Executive conclusion

**Three stored headers, not four.** An S3-compatible driver, R2 included, can store `Content-Type`, `Content-Disposition`, `Cache-Control`, `Content-Encoding`, `Content-Language` and `Expires` as object system metadata at write time, and R2 returns them on later GET. It cannot store an arbitrary header: `Content-Security-Policy` is not S3 system metadata and has no PutObject slot. The nearest thing, `Metadata` (`x-amz-meta-*`), comes back prefixed and is therefore inert as a CSP. So a public asset can be given a forced `Content-Disposition: attachment` and an honest `Content-Type` by the plugin at upload, but **cannot be given a CSP by the plugin at all**. Ticket 15's layer 2 genuinely cannot reach public placement, and layer 3's narrowed allowlist remains the only plugin-side cover there.

**The plumbing exists and is standard.** Laravel's `FilesystemAdapter::put()` passes its `$options` array straight through to Flysystem's `write()`/`writeStream()` untouched (it only special-cases a bare string as `visibility`), and `AwsS3V3Adapter` forwards any key in its `AVAILABLE_OPTIONS` list, which includes `ContentType`, `ContentDisposition` and `CacheControl`, into the PutObject params. No custom adapter, no AWS SDK call and no R2-specific code is needed: `Storage::disk($d)->put($key, $stream, ['ContentDisposition' => 'attachment; filename="..."'])` is the whole mechanism.

**A CDN base URL is already a disk setting, so the plugin should not invent one.** Laravel's `Illuminate\Filesystem\AwsS3V3Adapter::url()` returns `$this->config['url']` concatenated with the prefixed path when the disk config has a `url` key, and falls back to `$this->client->getObjectUrl(...)` otherwise. An R2 custom domain or an `r2.dev` public URL is configured there, by the application, exactly as research 03 concluded for buckets. The plugin should read `Storage::disk()->url()` and accept whatever host that produces, not take a CDN base URL of its own. Note `temporaryUrl()` has a separate `temporary_url` config key for the same purpose on signed URLs.

**Edge headers are real and are a deployment concern.** Cloudflare Response Header Transform Rules can set, add or remove response headers on proxied traffic, with a small reserved list that does not include `Content-Security-Policy` or `Content-Disposition`, and CloudFront response headers policies explicitly list `Content-Security-Policy` as an addable security header that can be configured to override the origin's. Both operate independently of the stored object. **But this only works on an R2 custom domain, not on `r2.dev`:** Cloudflare states that WAF rules, caching, access controls and Bot Management require a custom domain and "are not available when using the `r2.dev` development url". So an operator on a custom domain can put a CSP in front of public SVGs; an operator on `r2.dev` cannot, and `r2.dev` is documented as development-only anyway.

## Verified facts

### Laravel passes write options through untouched

- `FilesystemAdapter::put($path, $contents, $options = [])` normalizes a string `$options` to `['visibility' => $options]`, casts anything else to an array, and hands it to `$this->driver->writeStream($path, $contents, $options)` or `$this->driver->write($path, $contents, $options)` with no filtering. `writeStream()` wraps the driver call directly, "passing options through without modification". There is no interception of `ContentType`, `ContentDisposition` or `CacheControl` in the Laravel layer; only `parseVisibility()` translates a value, and it translates visibility alone. **Source:** [Laravel 13 `FilesystemAdapter`](https://raw.githubusercontent.com/laravel/framework/13.x/src/Illuminate/Filesystem/FilesystemAdapter.php), `put()`, `writeStream()`, `parseVisibility()`.
- `putFile()` and `putFileAs()` are convenience wrappers: `putFileAs()` opens the file as a stream and calls `put($path, $stream, $options)`, so the same options array reaches Flysystem on the uploaded-file path the plugin will actually use. `putFile()` delegates to `putFileAs()` with `$file->hashName()`. **Source:** [Laravel 13 `FilesystemAdapter`](https://raw.githubusercontent.com/laravel/framework/13.x/src/Illuminate/Filesystem/FilesystemAdapter.php), `putFile()` and `putFileAs()`.
- Laravel's documentation describes the third argument of `putFile`/`putFileAs` only as visibility, and documents no header options. The pass-through above is a source-level fact rather than a documented API surface, which matters for how much the plugin should rely on it. **Source:** [Laravel 13 filesystem documentation](https://laravel.com/docs/13.x/filesystem), sections "Automatic Streaming" and "File Visibility".

### Flysystem's S3 adapter forwards the header options

- `AwsS3V3Adapter::write()` and `writeStream()` both delegate to a private `upload()`, which builds the PutObject params through `createOptionsFromConfig()`. That method merges the adapter defaults, sets `params['ContentType']` when a `mimetype` config value is present, then copies every key listed in `$forwardedOptions` (defaulting to the `AVAILABLE_OPTIONS` constant) from the config into `params`, and copies `$multipartUploadOptions` keys to the option root. **Source:** [`thephpleague/flysystem-aws-s3-v3` `AwsS3V3Adapter`](https://raw.githubusercontent.com/thephpleague/flysystem-aws-s3-v3/3.x/AwsS3V3Adapter.php), `write()`, `writeStream()`, `upload()`, `createOptionsFromConfig()`.
- `AVAILABLE_OPTIONS` is: `ACL`, `CacheControl`, `ContentDisposition`, `ContentEncoding`, `ContentLength`, `ContentType`, `Expires`, `GrantFullControl`, `GrantRead`, `GrantReadACP`, `GrantWriteACP`, `Metadata`, `MetadataDirective`, `RequestPayer`, `SSECustomerAlgorithm`, `SSECustomerKey`, `SSECustomerKeyMD5`, `SSEKMSKeyId`, `ServerSideEncryption`, `StorageClass`, `Tagging`, `WebsiteRedirectLocation`, `ChecksumAlgorithm`, `CopySourceSSECustomerAlgorithm`, `CopySourceSSECustomerKey`, `CopySourceSSECustomerKeyMD5`. `EXTRA_METADATA_FIELDS` is `Metadata`, `StorageClass`, `ETag`, `VersionId`. **Source:** [`thephpleague/flysystem-aws-s3-v3` `AwsS3V3Adapter`](https://raw.githubusercontent.com/thephpleague/flysystem-aws-s3-v3/3.x/AwsS3V3Adapter.php), class constants.
- The consequence for this ticket: `ContentDisposition` and `ContentType` are forwardable through the standard `put()`/`writeStream()` options with no custom code, and there is **no key that carries an arbitrary response header**. `Metadata` is the only free-form slot, and it is the S3 user-metadata map.
- The `mimetype` config key is a second, Flysystem-level route to `ContentType` (`createOptionsFromConfig()` maps it explicitly), which is worth knowing because Flysystem otherwise detects the mime itself and would overwrite an intent the plugin cares about.

### S3 and R2 both treat these as stored system metadata

- S3's `PutObject` accepts `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Content-Type` and `Expires` as request headers, alongside arbitrary `x-amz-meta-*` user metadata. `Content-Security-Policy` is not among them. The docs also note that you "cannot use `PutObject` to only update a single piece of metadata for an existing object. You must put the entire object with updated metadata if you want to update some values." **Source:** [AWS S3 `PutObject` API reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), request syntax and request-header list.
- That last point is what makes stored headers an upload-time-only lever, consistent with ticket 13's "rules bind at ingest and at delivery, never at rest": changing a stored `Content-Disposition` on an existing object means rewriting the object (or a `CopyObject` with `REPLACE`), which is precisely the rewrite-at-rest the plugin has already ruled out.
- R2's S3 compatibility table marks `PutObject` as implemented with "System Metadata: ✅ Content-Type ✅ Cache-Control ✅ Content-Disposition ✅ Content-Encoding ✅ Content-Language ✅ Expires ✅ Content-MD5", and marks unimplemented: object tagging, object locking, website redirect location, KMS SSE, request payer, and **all ACL headers** (`x-amz-acl`, `x-amz-grant-*`). `CreateMultipartUpload` carries the same system-metadata support, and `CopyObject` supports `x-amz-metadata-directive` plus the same system metadata. **Source:** [Cloudflare R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/), object-level operations table.
- R2 documents the same headers as settable through its other interfaces: the Workers API `httpMetadata` object and Wrangler's optional flags set "the `Content-Type` (MIME type), `Content-Disposition`, `Cache-Control` and other HTTP header metadata". **Source:** [Cloudflare R2 upload objects](https://developers.cloudflare.com/r2/objects/upload-objects/).
- R2's custom metadata "fields map to the `x-amz-meta-`-prefixed headers used within the R2 S3-compatible API endpoint", and R2 adheres to RFC 2047 for Unicode in those values, decoding on storage and re-encoding on retrieval. This confirms that user metadata is returned prefixed, so it cannot masquerade as a `Content-Security-Policy` header on a browser GET. **Sources:** [Cloudflare R2 S3 API extensions](https://developers.cloudflare.com/r2/api/s3/extensions/) and [Cloudflare R2 Workers API reference](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

### Laravel's `url()` already accepts a CDN base URL

- `Illuminate\Filesystem\AwsS3V3Adapter::url($path)` reads: "If an explicit base URL has been set on the disk configuration then we will use it as the base URL instead of the default path." It returns `$this->concatPathToUrl($this->config['url'], $this->prefixer->prefixPath($path))` when `$this->config['url']` is set, and `$this->client->getObjectUrl($this->config['bucket'], $this->prefixer->prefixPath($path))` otherwise. **Source:** [Laravel 13 `AwsS3V3Adapter`](https://raw.githubusercontent.com/laravel/framework/13.x/src/Illuminate/Filesystem/AwsS3V3Adapter.php), `url()`.
- The same class exposes `providesTemporaryUrls()` returning `true`, and `temporaryUrl()` builds a presigned `GetObject` request whose base is replaced by `$this->config['temporary_url']` when that key is set. Signed-URL hosts and public hosts are therefore two independent config keys, which matters because R2 presigned URLs cannot be used with custom domains (research 03). **Source:** [Laravel 13 `AwsS3V3Adapter`](https://raw.githubusercontent.com/laravel/framework/13.x/src/Illuminate/Filesystem/AwsS3V3Adapter.php), `temporaryUrl()` and `temporaryUploadUrl()`.
- The documentation states this as a general rule under "URL Host Customization": "If you would like to modify the host for URLs generated using the `Storage` facade, you may add or change the `url` option in the disk's configuration array." **Source:** [Laravel 13 filesystem documentation](https://laravel.com/docs/13.x/filesystem), section "File URLs".
- `temporaryUrl()` accepts S3 request parameters as a third argument, and Laravel's own documented example is `['ResponseContentType' => 'application/octet-stream', 'ResponseContentDisposition' => 'attachment; filename=file2.jpg']`. This is a *private*-path lever (a signed URL can override disposition per request without touching the stored object) and does not apply to public assets, which are never signed. **Source:** [Laravel 13 filesystem documentation](https://laravel.com/docs/13.x/filesystem), section "S3 Request Parameters".
- Laravel's docs name Cloudflare R2 as a supported S3-compatible service reached by changing only credentials and the `endpoint` option. **Source:** [Laravel 13 filesystem documentation](https://laravel.com/docs/13.x/filesystem), section "Amazon S3 Compatible Filesystems".

### R2 public delivery: custom domain versus r2.dev

- A public R2 bucket is exposed either "as a custom domain under your control" or "using a Cloudflare-managed `https://r2.dev` subdomain for non-production use cases", and the two are independent. **Source:** [Cloudflare public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/).
- The split that matters here is stated flatly: "To use features like WAF custom rules, caching, access controls, or Bot Management, you must configure your bucket behind a custom domain. These capabilities are not available when using the `r2.dev` development url." **Source:** [Cloudflare public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/).
- `r2.dev` access "is rate-limited and should only be used for development purposes", and creating a CNAME pointing at an `r2.dev` subdomain is "an **unsupported access path**". **Source:** [Cloudflare public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/), public development URL section.
- A custom domain puts the bucket behind Cloudflare Cache (Smart Tiered Cache recommended), and by default "only certain file types are cached", with a Cache Everything page rule needed to cache all files. Access can be restricted with Cloudflare Access or WAF Token Authentication, but Cloudflare warns that the `r2.dev` subdomain must be disabled separately or "your bucket will remain publicly available through your `r2.dev` subdomain". **Source:** [Cloudflare public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/), custom domains section.

### Edge header attachment is available on both providers

- Cloudflare Response Header Transform Rules can "Set the value of an HTTP response header to a literal string value, overwriting its previous value", "Add a new HTTP response header with a literal string value without removing any existing headers", and "Remove an HTTP header from the response", statically or from a dynamic expression. Headers that cannot be modified are those starting with `cf-` or `x-cf-`, `server`, `eh-cache-tag` and `eh-cdn-cache-control`, plus a caveat that `cache-control`, `CDN-Cache-Control` and `Cloudflare-CDN-Cache-Control` set this way do not control Cloudflare's own caching. Neither `content-security-policy` nor `content-disposition` is on the reserved list. **Source:** [Cloudflare Response Header Transform Rules](https://developers.cloudflare.com/rules/transform/response-header-modification/).
- Cloudflare documents replacing or adding CSP headers on proxied traffic through exactly this mechanism, and warns that combining it (Add operation) with client-side security produces duplicate `Content-Security-Policy` headers. **Source:** [Content Security Policies (CSPs) and Cloudflare](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/content-security-policies/).
- CloudFront response headers policies do the equivalent on AWS: "CloudFront can remove headers that it received from the origin, or add headers to the response, before sending the response to viewers. Making these changes doesn't require writing code or changing the origin." The documented examples include "A set of common security headers, such as `Strict-Transport-Security`, `Content-Security-Policy`, and `X-Frame-Options`." A policy attaches to one or more cache behaviors, applies to both cached and forwarded responses, and "If the origin response includes one or more of the headers that are added in a response headers policy, the policy can specify if CloudFront uses the header it received from the origin or overwrites that header with the one in the response headers policy." **Source:** [AWS CloudFront: add or remove HTTP headers in responses with a policy](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/adding-response-headers.html).
- Both mechanisms are configured entirely outside the application: a Cloudflare dashboard/API/Terraform rule, or a CloudFront distribution setting. Nothing in either requires or permits application code, which is what makes this documentable rather than shippable.

## What remains unverified or uncertain

- **Which headers R2 actually emits on a public GET.** Cloudflare documents the system-metadata headers as *settable* on PutObject and as *stored*, but neither the public-buckets page nor the objects pages state the response headers returned when an object is fetched over `r2.dev` or a custom domain. The inference that a stored `Content-Disposition` is honored on a public GET is strong (it is the whole purpose of the field, and the S3 semantics R2 claims compatibility with) but is not stated in a Cloudflare sentence I could find. Worth an empirical check against a real bucket before the product ticket relies on it.
- **R2 support for S3 GET response-header override query parameters** (`response-content-disposition`, `response-content-type`). The R2 compatibility table's `GetObject` row lists conditional operations, Range, PartNumber and SSE-C, and says nothing about the `response-*` overrides either way; the extensions page does not mention them. Laravel's documented `ResponseContentDisposition` option on `temporaryUrl()` therefore has **unconfirmed** behavior on R2 specifically, even though it is standard on AWS S3. This only affects the private path, not this ticket's public question, but it is the obvious next thing someone will assume.
- **Plan availability for Response Header Transform Rules.** The Cloudflare page consulted does not state which plans include them, and the transform-rules quota per plan was not checked. An operator on a free zone may or may not have the rule slots.
- **Whether Cloudflare Cache interacts badly with a per-object `Content-Disposition`.** With a custom domain and Cache Everything, a cached response carries whatever headers were cached; nothing consulted describes header variance or purge behavior after a re-upload that changes stored metadata. Since ticket 13 forbids rewriting stored bytes at rest this may never arise, but a replaced object at the same key would.
- **The `Metadata`/`x-amz-meta-*` round trip on R2 through Flysystem.** RFC 2047 encoding on retrieval is documented by Cloudflare, and `Metadata` is in Flysystem's forwarded options, but whether Laravel surfaces those values anywhere readable (Flysystem's `EXTRA_METADATA_FIELDS` includes `Metadata`, but `FilesystemAdapter` exposes no accessor for it) was not traced. Any plugin use of user metadata would need its own read path via the S3 client.
- **No local dependency evidence.** As noted above, this repository has no `composer.json` or `vendor/`, so the installed Laravel and Flysystem versions could not be confirmed against a lockfile. If the plugin later pins `league/flysystem-aws-s3-v3` to a 4.x line, the `AVAILABLE_OPTIONS` list should be re-read, since it is the load-bearing constant for every write-time header claim here.
