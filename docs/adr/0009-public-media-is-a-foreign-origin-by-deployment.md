# Public media is a foreign origin by deployment, not by verification

Two earlier decisions rest on the same premise: [ADR-0004](0004-disposition-is-earned-not-assumed.md) refuses Active content on public placement, and [ADR-0005](0005-public-svg-is-sanitized-more-strictly.md) pays the Strict pass's compatibility cost there, both because a public asset resolves to the disk's own URL and never reaches the Delivery route. That reasoning assumes the disk's URL is a *foreign* origin. It is not automatically true: a public bucket fronted by a CDN on the application's own domain is same-origin with the panel session, which makes public placement more dangerous than private rather than less, since private at least carries the Delivery route's content policy and Disposition rule.

The plugin assumes the foreign origin and does not verify it. Serving a public media host that is not the panel's origin and shares no cookie scope with it is stated as an operator obligation in the README, alongside the concrete thing it protects: a Sanitized SVG is the only Active content that can reach public placement at all, so it is the whole exposure.

The rejected alternative was detecting the case, by comparing the disk's configured `url` host against the application host and refusing or warning. It fails in both directions in exactly the deployments that have the problem: a reverse proxy, a CNAME, a sibling subdomain sharing a parent cookie domain, and an `APP_URL` that need not match the panel's real host. A check that both misses real same-origin deployments and fires on safe ones buys a false sense of cover, and shipping it later would begin refusing uploads in deployments that work today, so the assumption is recorded here rather than half-enforced in code.
