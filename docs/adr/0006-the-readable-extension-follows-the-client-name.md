# The readable extension follows the client name, the object key follows the bytes

Every upload is sniffed, so the plugin often knows a file's real mime type contradicts the extension the client sent: `report.txt` that is actually a PDF. The plugin does not reconcile them. The extension persisted alongside the Original filename is taken from the client's name and lowercased, while the extension appended to the `object_key` is derived from the resolved mime type. The two are allowed to disagree on the same asset, permanently.

The split is a split of purpose. The readable name exists to show what the person uploaded, and rewriting `report.txt` to `report.pdf` puts words in their mouth on the strength of a heuristic. The object key exists to be handed to a storage provider, whose content handling and any CDN in front of it key off the suffix, so there the sniffed truth is the only useful answer. Nothing safety-relevant rests on the readable extension: `mime_source` records how far the mime type can be trusted, and disposition (ADR 0004) is earned from that rung rather than from the filename, so a mislabelled file is served as a download regardless of what its name claims.

The rejected alternative was normalizing the readable extension to match the sniff, which reads as the tidier option and is what a reader is most likely to try to "fix" later. It was rejected for two reasons: it destroys provenance in the one field whose whole job is provenance, and it is not reversible once written, because the original suffix is gone. The cost accepted in exchange is that a library will contain assets whose displayed name disagrees with their served type, which is a truth about the uploaded file rather than a defect.
