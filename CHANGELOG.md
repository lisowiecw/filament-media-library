# Release Notes

## [Unreleased](https://github.com/lisowiecw/filament-media-library/compare/v0.1.0...main)

- BlurHash at upload: an uploaded image carries its hash before its card is ever drawn, so a fresh upload paints colour rather than a grey tile while its thumbnail is still being generated. The hash is computed inline in the ingest request, from bytes already on local disk, and written in the insert that was happening anyway: nothing is scaled, encoded or written to the object store, and no job is queued to produce it. A file whose bytes will not decode still uploads; the failure is recorded so nothing asks again. The hash now carries a status of its own, `pending`, `ready` or `failed`, on the new nullable `media_assets.blurhash_status`, where an absent status means nobody has ever asked and is a different thing from a recorded failure. Existing rows that already hold a hash are backfilled as ready, so the migration asks the operator for no data decision. An SVG or a small original is neither hashed nor asked about, since it paints itself, and a non-image is never hashed at all. The thumb job keeps writing the hash, now strictly as a top-up: it fills in an asset that has none, never overwrites a ready one, and never turns a recorded failure ready by the side door. See [ADR 18](docs/adr/0018-the-blurhash-is-computed-apart-from-the-derivative.md).

- The page you are looking at is the page that gets served: one render may now queue a whole page of cards, `media-library.derivatives.lazy_dispatch.per_request` rising from 5 to 48, which is the library grid's own page size. The old value was smaller than any real page, so a first view of a freshly imported library could never be complete by construction, and most of its cards waited for a later visit. The per-minute cap is unchanged at 60 and keeps its role as the real protection: it is what bills the operator for object-store reads and writes, and it is what stops a long scroll queueing without bound. Both halves stay configurable, so an operator who wants the old trickle sets `per_request` back to 5.

- BlurHash on first view: an asset that arrived by import has no bytes in hand at adoption, so the first card that wants a hash is what asks for one, and the asset costs a single extra read the first time somebody looks at it. Import runs queue nothing themselves, because a run that touched every object is exactly the cheap re-run the Import report exists to protect. A hash in flight is marked pending in the database before the job is queued, and the claim is what stops two renders of the same card asking twice; a recorded failure is never asked about again, however often the card is drawn. An asset that paints itself, a sanitized SVG or a small original, and anything that is not an image, are never asked about at all, which is the same question `Derivatives` already answers for a thumbnail. Hash work is capped on its own terms under the new `media-library.blurhash.lazy_dispatch` keys, defaulting to 300 a minute against the derivative cap's 60, because a hash is a read and a decode that writes nothing to the object store; spending one allowance does not spend the other. Hashing rides on the render, so it reaches nothing the grid would not already offer, tenancy included.

- A thumbnail arrives without a reload: the library grid and a picker's inline attached items repaint a card in place as its hash and its thumbnail land, so the seconds after an upload no longer end in a grey tile that only becomes a picture if the person navigates away and back. Asking is conditional on there being anything to wait for. A surface emits the poll only while a card on the page in hand is unresolved, and stops emitting it once every card is ready or has failed, so an idle open modal over a fully generated library polls not at all. Failure counts as resolved on both halves, the hash and the rendering, because a page whose only unresolved card is a file that will never decode must stop asking rather than request forever. A card the viewer may not be delivered is a glyph tile for good and is waited on by nothing. The interval is `media-library.poll_interval`, defaulting to `3s`, and asking pauses while the surface is scrolled out of view. A field given a `thumbnailUsing()` rule of its own never asks, on either surface, since the package's pipeline is then not what its cards wait for. The Filament resource table is deliberately unchanged: a reload is natural there.

- An operator backfills an existing library from the command line: `media:regenerate-derivatives --hashes` queues a BlurHash for every asset owed one, so a library that predates hashing fills in without having to be browsed card by card. It rides the regeneration command rather than adding one of its own, because the selector, the dry run and the pacing are already there, and it queues hash work and no derivative work, so it refuses to be combined with `--missing`, `--failed`, `--stale` or `--variant`. The run obeys the hash allowance rather than the derivative one and waits out a spent minute rather than refusing, so a run over a large library finishes; its wall time is the library's size over `media-library.blurhash.lazy_dispatch.per_minute`, and `--dry-run` queues nothing, reports what a real run would queue and says how many minutes it would take at the configured rate, which is how an operator finds that out beforehand. An asset with a ready hash, a recorded failure, a computation already in flight, or nothing a hash could be made of, is never asked again.

- A hash left pending by a worker that died is asked for again: an asset pending longer than `media-library.blurhash.abandoned_after` seconds, 15 minutes by default, is read as nobody's work and the next view or backfill may take it. A worker killed outright, by an OOM, a `kill -9` or a deploy that stops the queue mid-job, runs neither the computation nor the failure hook, so its assets kept the pending status for good and their cards stayed grey however often anybody looked. The window is timed from the new nullable `media_assets.blurhash_pending_since`, written where the status is taken and cleared wherever it settles, because `updated_at` moves for reasons that have nothing to do with hashing. The migration backfills nothing and asks the operator for no data decision: a pending row with no recorded time is exactly one this stranded, so it is reclaimable on the first view after the migration. Inside the window nothing changes, a hash in flight is never asked for twice, and two views meeting the same abandoned asset still queue one job between them. A ready hash is never overwritten and a recorded failure is never reopened by this path. The claim travels with the job, so a worker whose claim lapsed while it was still retrying settles nothing when it finally gives up: the failure would otherwise close the question against the live job that replaced it and leave an asset that could be hashed recorded as one that cannot. The backfill reports a lapsed claim as `abandoned` rather than as an asset never asked, so a dry run says which of the two a real run would be doing.

- A rendering left pending by a worker that died is generated again: a derivative row pending longer than `media-library.derivatives.abandoned_after` seconds, 30 minutes by default, stops counting as work in flight, so the next render of the card queues the job again and `media:regenerate-derivatives --abandoned` selects the whole set for an operator who would rather not wait to be browsed. A worker killed outright, by an OOM, a `kill -9` or a deploy that stops the queue mid-job, records neither the success nor the failure, so its rows sat at pending for good and no selector could reach them: the card painted the quiet tile on every render from then on. There is no new column, because `media_derivatives.updated_at` is written by the pipeline and nothing else, which is the whole difference from the asset row that needed one. The health readout counts abandoned rows on a line of their own, and the four counts stay disjoint, so what an operator is shown is what a run then queues. `GenerateDerivative` now fails on timeout, so a generation that merely hangs settles its row rather than waiting out the window. A failed row is still never re-dispatched by a render at any age, a ready one is still served however stale its digest, and a regeneration overwrites in place, so nothing is orphaned in the object store. See [ADR 19](docs/adr/0019-a-pending-derivative-ages-on-its-own-updated-at.md).

## [v0.1.0](https://github.com/lisowiecw/filament-media-library/compare/...v0.1.0) - 2026-09-01

Initial pre-release.

- Refusals that reach the person: a file the ingest floor turns away now says so in words wherever it was offered, and says the whole of it. Both the title and the body of a Filament notification go through an HTML sanitizer, which parsed the `<style>` a refusal names as a tag and swallowed the rest of the sentence, so a person read half a reason; refusal text is escaped in one place on its way to a notification and arrives intact. The picker absorbs a refusal on both of its ways in, the drop on the field trigger and the upload through the Library modal, where it previously threw past the field and the file simply never appeared. A refusal costs the one file and not the gesture: the rest of a multi-file drop is still ingested, in the order it was dropped, and the notification names what was refused beside the count of what was not.

- A runnable workbench: `composer serve` boots a Filament panel the plugin is registered in, with an Article resource carrying two `MediaPicker` fields between them covering single and `multiple()`, `reorderable()`, `droppable()`, `acceptedFileTypes()`, both visibilities and `scopeLibrary()`, plus the management page. The seed goes through `IngestService` rather than around it, so the rows are the rows an upload would have written, and it leaves both visibilities, images and documents, two uploaders, four uploaded spans and both attached and unattached assets, which is what the facet sidebar and the usage list need before they say anything. The workbench writes the permissive policy and gates a host application writes, so the packaged deny-everything default is not what makes the example look broken, and the panel is deliberately untenanted. The suite now reads the workbench: `Article` lives at `Workbench\App\Models\Article` and its table comes from the workbench migration. Nothing here ships to a host application.

- Filament 4 matrix: the `^4.0||^5.0` constraint is proven rather than claimed. One suite runs against both majors on every push, with no job or step allowed to continue on error and a single `matrix` job standing behind every leg, so branch protection has one stable name to require and a red Filament 4 job blocks a release. A release guard refuses a tag or a published release whose commit does not carry a passing `matrix` check, so the blocker holds without branch protection too. The shared-API limit is enforced rather than described: a test reads every Filament symbol `src/` imports and asserts the installed major declares it, so a v5-only class fails the Filament 4 leg. The README compatibility table is generated from that matrix by `composer compat:sync` and a test fails when the two drift apart, so a version tested in CI and a version advertised in the README cannot disagree quietly. The build stays Filament 5 first: a test refuses version sniffing anywhere in `src`, so any v4 accommodation has to sit behind the plugin and field APIs both majors share rather than as a branch on the installed version. Ending v4 support is documented in [UPGRADING](UPGRADING.md) as one commit that narrows the constraint and drops the job together. Visual and interaction parity between the majors is explicitly not promised.

- Import drift: `media:import --check-drift` compares an already-present asset to what the disk now says about its object, and repairs nothing. It reads the size and the mime ladder for every row the run already holds, which is exactly the cost the default path avoids, so it is a flag rather than a default: without it an already-present row still costs one query and no object read. A drift line names the object key, the field, the recorded value and the value storage reports, and an object that has gone under an already-present row is reported as its own case rather than as a value that merely differs, since every other comparison would then be against nothing. The mime type is compared only where the run's ladder landed on the rung the row records, because which rung answers is decided by whether the run was given `--sniff`: a sniffed row checked without paying for a read would otherwise be called drifted on an untouched object. Drift appears in the JSON report as its own list beside the omissions, with a count of its own, because nothing on it was declined. Nothing is written, ever: the item is reported and exited, and there is no repair mode.

- Rich text attachments: `IngestService::ingest()` is promised surface, so a `RichEditor` wired through `saveUploadedFileAttachmentsUsing()` files its inline uploads through the same entry point the picker and the management page use, instead of writing to a disk the library has never heard of. The whole floor applies on that path unchanged: blocked types, the configured accepted types, family mismatch, SVG sanitization and its strict pass, the refusal of active content on public placement, the stored headers, and the tenant and uploader stamps. The `Placement` argument is now optional and falls back to the configured one, which is additive. `IngestService::ingest()` is named in the Promised surface accordingly. The README recipe records an External reference beside the asset so it counts as used, blocks a delete and is never swept as unattached, and requires public placement, because a private asset resolves to a signed Delivery URL and a signed URL saved inside HTML rots on its own expiry. Revoking the reference when an image leaves the body is the application's to trigger: the package does not read saved HTML. No second picker surface and no editor plugin.

- Tenancy: `MediaLibraryPlugin::make()->tenantUsing(fn () => Filament::getTenant())` tells the library who the current tenant is, per panel, defaulting to the panel's own tenant where the panel has tenancy; leave it unset and nothing here applies, so a single-tenant application is untouched. The tenant is stamped onto the nullable indexed `media_assets.tenant_id` once at upload and never reassigned, and a write that tries to move an asset between two tenants throws. Scope decides what is offered and the policy decides what is delivered (ADR 7): the picker and the management page query within the current tenant, and `view` separately refuses an asset outside it, so a route-model binding or a guessed URL cannot sail past a boundary a query merely narrowed. A cross-tenant Delivery request answers 404 rather than 403, since 403 would confirm the asset exists. An untenanted asset belongs to no one rather than to everyone, which is what makes configuring a resolver over an existing library safe: it goes quiet rather than appearing in every tenant at once. Claiming brings it back, one way and allowed once, through `media:assign-tenant` (with `--asset=` and `--dry-run`) or a bulk action on the unscoped listing; the fail-closed `viewAllTenants` ability is what unlocks that listing, as an "All tenants" toggle, a tenant column and a tenant facet. An attachment made before tenancy existed still counts as usage and still blocks deletion, while its tile degrades to a dimmed glyph, and attaching anything new across the boundary is refused in the picker and in the reconciler alike. `media:import` now requires `--tenant`, accepting the literal `none`, so a run says who the adopted objects belong to rather than leaving it to be inferred. **This is a breaking change** for anyone scripting the importer: add `--tenant=none` to reproduce what a run did before. Jobs and commands are neither scoped nor policy-checked, and the plugin never inspects the host model's own tenancy.

- Importer: `media:import --model= --column= --disk= --field=` adopts the uploads an application already has, registering each object in place so every URL that worked before the run still works after it. The legacy path becomes `object_key` verbatim, its basename `original_client_filename` and its stem `display_name`; size comes from the disk and the mime type from a ladder of stored header, then `--sniff` where the operator pays for a read, then extension, then nothing, writing `mime_type` and `mime_source` together. Identity is the unique disk and object key pair resolved with `firstOrCreate`, so a re-run adopts nothing twice and a name a person edited afterwards survives it. `--copy` is opt-in, writes to a key derived from the pair it came from rather than a freshly generated one, so a re-run copies nothing twice (ADR 14), asserts that key is free, and never touches the source; there is no move mode. Visibility is the operator's `--visibility`, else a local disk's file mode, else the disk's configured value, else private, and is never read back from an `s3` driver, which R2 does not answer. Adoption is not ingest: the size ceiling and the family checks do not apply, but the denylist does, and a blocked path is reported rather than stored. An unknown disk or model fails the run before anything is written, as does a disk that cannot deliver the declared visibility, which is the same invariant a field placement is held to. `--uploader` names the column provenance comes from and a mistyped one fails the run rather than quietly producing a library nothing is attributed in; a row that simply has no uploader stays null. A missing object writes no row. The command is isolatable on its model, column and disk, so two imports of one source cannot interleave. Every run leaves a console summary and a JSON report naming its omissions rather than its successes, at `--report` or a run-timestamped path under `storage/logs/`; `--dry-run` writes the same report and no rows.

- Importer attachments and traversal: `media:import --field=` is now the field context the attachment rows are written against rather than a report label, so a host row finds its assets again once the legacy column is gone. `--cardinality=single|many` is declared and never inferred, and a column read against the wrong one ends the run in either direction, as does a nested object or a URL; a run with no `--field` adopts as before and attaches nothing. In a multi-value column the array index becomes the attachment order verbatim, and mess inside it, a duplicate, an empty element, or a path whose object has gone, is skipped and reported against its index while the rest of the row is attached. Attachment writes resolve on host, field and asset, so a second run adds nothing and never rewrites an order a person set in the picker afterwards, and an asset a previous run adopted is attached rather than passed over. `--source=disk --prefix=` is an explicitly degraded fallback for a layout with no column to read: it walks the prefix lazily through `listContents()` rather than materialising it, records the prefix as `import_source`, and refuses `--field` and `--uploader` rather than ignoring them, since a key on a bucket names no host row. The report separates skipped elements from omitted rows, counts what it attached, and is written even when a bad column shape ends the run partway.

- MIME re-resolution: `media:resolve-mimes` is the second step of a migration, re-running the mime ladder over the assets sitting on one rung and writing `mime_type` and `mime_source` together, so a row never claims a rung it did not come from. It selects on `--from=`, defaulting to `extension`, which is where an import that only adopted objects leaves most rows, and it reads no bytes at all unless `--sniff` says to, because a sniff is one full read of every object it touches and the bill is the operator's. A sniff now outranks a stored header everywhere the ladder runs, the importer included: a header only repeats what whoever wrote the object claimed, so a run that has paid for the read is never overruled by a claim, and on a bucket where every object carries a `Content-Type` the flag buys something rather than nothing. A pass only ever raises what a row claims and never lowers it, so a disk with less to say today than at import leaves the row alone; `--dry-run` reports the rung transitions and writes nothing. The two `--sniff` flags are deliberately never chained: `media:import` and this command are separate decisions about the same bill, and the window between them is the `mime_source` facet on the management page rather than a banner. Resolution never happens on the Delivery route, so a read path performs neither the write nor the fetch. Until the pass has run, a freshly imported library renders as downloads, which is ADR 4 working rather than failing.

- Saved filename: `MediaLibraryPlugin::make()->downloadFilenameUsing(fn (MediaAsset $asset): string => ...)` decides what a saved file is called on the viewer's disk, for the whole application at once. The default is exactly what the package answered before, `original_client_filename ?? display_name`, so this is additive. The one resolver names both the Delivery route's `Content-Disposition` and the `ContentDisposition` written onto the stored object at upload, so a disk that ignores response overrides serves the same name the route would; the stored header now carries a filename where it previously carried the bare disposition. The resolver sees the asset alone and never a host model, since an asset can be attached in many places and the stored header is written before any attachment exists. Its answer is scrubbed by the Readable name rules and given the asset's own extension where it returns a stem without one, so a resolver cannot break or inject a header. An asset with no name at all, which is a row not saved yet rather than anything the library holds, is called `download` instead of being left for the disk to name after its object key.

    The stored header binds at upload and is never rewritten, so it is the resolver that both places share rather than the answer: a Display name edited afterwards moves the route's header and leaves the stored one where it was.

- Paired disks: `media-library.public_disk` and `media-library.private_disk` (`MEDIA_LIBRARY_PUBLIC_DISK`, `MEDIA_LIBRARY_PRIVATE_DISK`) name the two buckets of a two-bucket deployment once, so a field that declares only its visibility lands in the matching one instead of repeating `->disk(...)` at every call site. Disk resolution reads field disk, then the visibility's paired disk, then `media-library.disk`, then `filesystems.default`, so `media-library.disk` now applies only when the visibility's half of the pair is unset. Naming neither half leaves resolution byte for byte what it was, so this is additive.

- Disk and visibility invariant: a placement whose disk cannot deliver what its visibility promises is refused when the placement resolves, with `PlacementMisconfigured` naming the field, the disk, the visibility and the rule broken, so a misconfigured field fails on the first render rather than writing an asset nobody can fetch or anybody can. Two rules: a public placement on a declared disk with no `url` key, and a private placement on a disk the application declares public, as `public_disk` or with `'visibility' => 'public'` on the disk itself. The check reads configuration only, never the provider, since R2 answers no ACL call. Set `media-library.enforce_disk_visibility` (`MEDIA_LIBRARY_ENFORCE_DISK_VISIBILITY`) to false where a public disk is deliberately served through the application's own origin. **This is a breaking change**: a public field on a disk declared with no `url` now throws where it previously stored, which is the bug it closes. Give the disk a `url`, or set the flag to false, before upgrading.

- External references: `$asset->attachments()->createExternal($identifier, $label)` records that something outside any host model uses an asset, as an attachment with a null host. It counts as usage and blocks deletion through the existing mechanism rather than a second one, is excluded from every field-context query so `HasMedia` never returns it, and is withdrawn with `revokeExternal($identifier)` or per row from the management page's usage panel, behind the `detach` ability. Host-model rows are not removable there or through either revoke: detaching stays on the host record. `MediaAsset::attachments()` now returns the `Attachments` relation rather than a plain `HasMany`, which is additive for anything already reading or querying it.
- Library management page: `MediaLibraryPlugin::make()->withLibraryManagement()` opts a panel into `MediaAssetResource`, a table listing every asset including the private and (behind the trashed filter) the soft-deleted, gated on `viewAny`. The asset's own page paints the preview rendering of an image, generated on that first look. It renames, deletes, restores, force deletes, downloads and uploads, and deliberately cannot replace bytes in place, change visibility or move an asset between disks or directories. `UsageList` feeds the usage column, the view page's panel and the force-delete confirmation alike; the disk and object key are copyable there, `import_source` and `mime_source` are shown, and `source` and `mime_source` are filterable. Cleanup gets an unattached filter with a grace-period preset and a bulk delete restricted to it, with eligibility recomputed at the moment of the delete; bulk delete and bulk restore report their per-row skips and there is no bulk force delete. A health readout shows the failed, missing and stale derivative counts and queues a bounded batch, naming `media:regenerate-derivatives` for the rest. The importer stays CLI-only.
- Lifecycle and cleanup: detaching touches the attachment row alone, while deleting soft-deletes the record and queues removal of the backing object and every derivative alongside it, on the queue's own retries and into `failed_jobs` when they are exhausted. `AssetLifecycle::delete()` is blocked while anything references the asset and carries the usage list on the refusal; `delete(force: true)` overrides it and takes the attachment rows with it. One resolver, `UsageList`, answers "what uses this" everywhere, reading a host model's own `mediaUsageLabel()` where it offers one, and an attachment whose host row has gone still counts as a use. Restoring an asset brings back the record alone, leaving its renderings to be regenerated lazily. `media:unattached-assets` reports assets nothing has referenced for longer than `unattached_grace_days` (30 by default, overridable with `--days`), deletes nothing, and is not scheduled: installing the package schedules nothing. Every one of these rules is package-global and no field can override it. The grace period counts from when an asset last stopped being referenced, recorded on `media_assets.unattached_since` as the last attachment row goes and cleared when one is created, falling back to the upload date for an asset nothing ever referenced; existing rows are backfilled with their upload date, so the reported set is unchanged on the day the migration runs.
- Derivative staleness and regeneration: a derivative records a digest of the target edge and quality that produced it, so a settings change is detectable by comparison; a null digest means unknown rather than stale, and a stale rendering is still served silently. Nothing sweeps and nothing regenerates on render. `media:regenerate-derivatives` takes `--missing`, `--failed`, `--stale`, `--variant` and `--dry-run`, obeys the same per-minute cap as lazy backfill, and leaves an existing rendering ready and its digest in place until the refresh has actually been written. A derivative URL carries the digest recorded on the row rather than the one the current settings would produce, on the public disk URL as well as the Delivery route, so the URL moves when the bytes move and an in-place overwrite is never masked by an immutable cache. `DerivativeHealth::stale()` and `DerivativeHealth::failed()` are the counts a management page shows.
- Preview on demand and variant delivery: a private derivative is addressed through the Delivery route's `variant` parameter, which re-checks `view` against the asset it already loaded and streams the rendering with `Cache-Control: private, immutable`; no presigned derivative URL is ever handed out. A derivative URL's expiry is quantized to a configurable bucket (six hours by default), so it is byte-stable inside its window and the cache actually hits, while an original keeps its five-minute per-render signature; the settings digest rides in the URL, so a regeneration under changed settings is never masked by a cached response. `$asset->previewUrl()` resolves the 1600px `preview`, generated on its first actual request and never at upload.
- BlurHash placeholders: a card standing in for a thumbnail paints the asset's own BlurHash, decoded in PHP and painted as CSS gradients, so the package still ships no JavaScript and no stylesheet. The hash stays on the tile as `data-blurhash` for an application that wants to decode it properly over the top.
- Thumb derivatives: a grid card paints a `thumb` derivative, 400px on the longest edge and WEBP, generated off the request cycle and stored beside the original under the parent's placement and visibility. A missing derivative at render time queues the job and paints the pending tile, rate-capped per request and per minute; a small browser-renderable original is its own thumbnail and registers no rows at all. **This adds `ext-gd` to the package's requirements**, so check for it before upgrading.
- Library grid: the picker's modal opens on a Library tab that offers what the field accepts, searched by one input across name, filename, alt text, uploader and object key, loaded 48 at a time to an end marker, with the live ordered selection in the footer.
- Public placement: `$asset->url()` is the supported way to address an asset, resolving a public one to the disk's own URL so CDN and browser caching survive, and a private one to the signed Delivery route. `$asset->downloadUrl()` always resolves to the route, since a link cannot tell the browser to save a foreign origin's response.
- Authorization and delivery: a fail-closed `MediaAssetPolicy`, the `uploadMedia` and `attachMedia` gates, and one signed Delivery route per panel that re-checks `view` on every request, earns its disposition, and carries a restrictive content policy on every response.
- Package skeleton: service provider, `MediaLibraryPlugin`, `config/media-library.php`, and a Testbench harness hosting a real Filament panel.
